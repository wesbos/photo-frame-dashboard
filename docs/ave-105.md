# AVE-105 Frameo frame (RK3326, Android 9 Go)

One unit assessed and tested on 2026-10-15 and 2026-10-17 using macOS on Apple
Silicon and network ADB. This is a device report, not a flashing profile for
other RK3326 frames. The retail listing was not recorded.

**Result:** shipped `su` provides root, and an adapted, platform-signed Rockchip
Android 9 donor SystemUI runs from userdata. Status/navigation bars, quick
settings, classic Recents, and injected touch pull-down work. Automatic startup,
recovery after process death, physical touch confirmation after the final fix,
and reboot persistence remain unfinished. See the
[SystemUI investigation](ave-105-systemui-investigation.md) for donor provenance,
the publicly published signing key, resource incompatibilities, and fixes.

## Access and stock firmware

Network ADB works on TCP port 5555. The original enabling procedure was not
recorded. `ro.adb.secure=1` is set, but rejection of an unknown host key and ADB
persistence across reboot have not been tested. USB ADB, loader entry, and
offline recovery have not been tested on this unit.

Read-only identity/root checks, using the owner's current address:

```sh
adb connect <frame-address>:5555
adb -s <frame-address>:5555 shell getprop ro.build.fingerprint
adb -s <frame-address>:5555 shell getprop ro.product.cpu.abi
adb -s <frame-address>:5555 shell su -c id
```

No exploit or boot patch was required for root. The system root filesystem is
read-only; vendor was mounted read/write. Verified-boot properties reported an
orange state and enforcing verity. These observations do not authorize or prove
that changing a verified partition will boot successfully.

SystemUI was absent from the initial package list, including uninstalled
packages; searches of `/system`, `/vendor`, and `/oem` found no SystemUI APK.
The installed `com.android.systemui.theme.dark` package is an overlay. Framework
status-bar, notification, and window services were present. The wallpaper
Binder service was absent, although its framework code remains present.

`android.rockchip.update.service` 1.8.2 is installed and enabled with
boot/connectivity receivers and update permissions. Its automatic update
behavior has not been analyzed. Frameo and the updater were not disabled.

## Launcher and apps

An experimental local launcher, Frame Apps (`com.photoframe.launcher`), was
installed and selected as HOME. Version 1.1 lists launchable apps with icons
and provides an Android Settings button. Its source is outside this report's
scope. The repository's [floating Home app](../scripts/home-button/README.md),
`com.photoframe.homebutton`, was also installed and tested. ADB taps verified
opening Settings and returning Home; those checks do not prove a panel-operated
recovery path or boot startup.

Firefox, Firefox Home, and Synology Photos were already installed at assessment.
Chrome 138.0.7204.179 (`armeabi-v7a`) was subsequently installed and launched.
During later use with Chrome open, the event log showed widespread process
deaths and low-memory events, including SystemUI, the launcher, Settings, and
Frameo. Chrome also became unresponsive. Closing Chrome recovered available RAM
to about 675 MiB, and manually starting the existing SystemUI restored both
bars. This is one observed failure, not a compatibility guarantee or proof that
all Chromium builds behave the same way. See the
[memory-pressure findings](ave-105-systemui-investigation.md#memory-pressure-and-persistence).

## Backup findings and limits

A capture of the eMMC prefix before userdata was stopped after slow Wi-Fi
transfer (about 0.2 MB/s). That incomplete capture is not restorable. A prefix
alone would also exclude userdata, trailing GPT, and hardware boot areas.

Later small captures of `uboot`, `trust`, `dtb`, `dtbo`, and `vbmeta` passed exact
size, gzip CRC/readback, filler checks, and independent on-device SHA-256 checks.
The `boot` capture was truncated and its retry was declined. There is **no
verified full-device, boot, system, recovery, or userdata backup**. Saved
package/settings metadata supported the userdata app trial; it is not firmware
recovery, and live package databases must not be overwritten as an app rollback.

SuperSU's raw binary stdout expanded LF to CRLF, corrupting initial transfers.
For small reference files, base64 encoding inside the root shell, followed by a
brief delay before root-shell exit, produced captures that matched independent
size/hash checks after host decoding. Encoding alone did not prevent exit-time
truncation. This transport observation is not a verified bulk-backup procedure.

No system, vendor, or boot partition was modified for the launcher or SystemUI
trials. Follow the [backup and recovery rules](../README.md#rules-we-learned-the-hard-way)
before any future partition changes. Private backups and per-frame recovery
records are excluded from the repository.

## Remaining work

- Verify navigation and the Settings → Apps recovery path by hand on the panel.
- Resolve SystemUI background-service policy, startup, and recovery after
  process death, then test reboot persistence with an agreed recovery plan.
- Test wallpaper-service restoration; the prepared overlay has not been enabled.
- Obtain a complete verified backup before considering firmware changes.
- Review the updater and verify ADB authentication enforcement.

Android's patch level is old, SELinux is permissive, root shell access has no
observed prompt, and a publicly published platform development key matches this
firmware. Use an isolated network and limited accounts. Arbitrary installed
apps' access to `su` was not tested.

Upstream issues and PRs were checked for `AVE-105` before this report; no matching
report was found. Other RK3326 models have different Android versions, storage,
and partition layouts. Their firmware and setup scripts are not interchangeable.
