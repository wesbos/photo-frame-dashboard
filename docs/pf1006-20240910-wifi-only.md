# PF1006 / AiMOR 6.0.26 (`20240910`): root ADB over Wi-Fi with no USB port

One unit, from macOS on Apple silicon, on 2026-10-15 and 2026-10-16. This frame has **no USB port
at all**. Every USB route in this repo (T3, Route U, the recovery-window write) was out, and so was
FEL. Root ADB came entirely over Wi-Fi, through AiMOR's own command channel
([T3c](pf1007l-start-here.md#t3c-temporary-adb-through-the-aimor-connection)), and was then made
persistent with one `/data` property. **Nothing was written to the boot partition or `/system` to
get access.**

This is the same firmware as the unconfirmed unit in
[PR #142](https://github.com/wesbos/photo-frame-dashboard/pull/142). It is a different build from
the PF1006 V43 in [PR #151](https://github.com/wesbos/photo-frame-dashboard/pull/151), which has a
USB-C socket and much older AiMOR (3.2.76). Unit report issue:
[#159](https://github.com/wesbos/photo-frame-dashboard/issues/159).

## What worked, in order

### 1. Read-only checks

- `nc -vz <frame-ip> 5555`: refused, so there is no stock network ADB.
- `nc -vz <frame-ip> 8086`: open. That's AiMOR's paired file service, and a reliable way to
  confirm a host is the frame.
- To find the frame after it changes address, ping-sweep the subnet and look for its MAC prefix
  (the first four bytes stayed the same across reconnects on this unit), then check port 8086 or 5555.

### 2. Factory test app (optional; no ADB on its own here)

An empty `license.properties` at the root of a FAT32 SD card
([PR #125](https://github.com/wesbos/photo-frame-dashboard/pull/125)) **works on AiMOR 6.0.26**:
- It worked from the first FAT32 partition of a Raspberry Pi OS card, so no reformat was needed.
- Inserting the card opened the manufacturer screens. Five taps top-left opened the test app.
- About → tapping Model also opens the "Open test app" password dialog
  ([#135](https://github.com/wesbos/photo-frame-dashboard/issues/135)).

Flipping **IS CLOSED → IS OPEN** set `persist.sys.usb.config=mass_storage,adb`. **On a frame with
no USB port, that does nothing useful:** 5555 stayed closed. Skip this step unless your unit has
USB.

### 3. T3c through a router DNS record

The frame's Wi-Fi screen has no Modify network, so there is no per-device DNS. Instead:

1. **UniFi:** add a local DNS A record `imsconnect.efercro.com → <Mac LAN IP>`. Check it:
   `dig @<router-ip> imsconnect.efercro.com A +short` should print the Mac's address.
   The AAAA lookup returned only the vendor CNAME, with no address, so IPv6 did not bypass it.
2. With nothing listening on the Mac yet, turn the frame's Wi-Fi off and on. AiMOR showed a
   **"Server connection" error**: the redirect works, and the vendor was never reached. (Other
   firmware shows "error 002" here.) Then find the frame's current IP.
3. Start the repo's one-shot listener:

   ```sh
   /usr/bin/python3 scripts/aimor-network-adb/server.py \
     --bind <mac-lan-ip> --frame-ip <frame-ip> --seconds 600
   ```

   AiMOR reconnected **without another Wi-Fi toggle**:

   ```text
   {"event": "received_frame", "command": 110009, "payload_bytes": 414}
   {"event": "runtime_adb_command_sent", ...}
   ```

4. `adb connect <frame-ip>:5555` → `device`, and `adb shell id` → **`uid=0(root)`**.
   AiMOR 6.0.26 therefore has the same 12009 root-shell handler as 6.0.78, on the same
   `imsconnect` host.

No `dns.py` was needed. The Mac's application firewall was off.

**Don't use macOS Internet Sharing for this.** We tried it before the router record:
- Turning it on cut the Mac's internet for a while.
- `mDNSResponder` holds port 53 on the shared network, so `dns.py` can't bind there.
- The frame (Android 6) never joined the Mac's access point.

### 4. Make it persistent (no flash write)

```sh
adb -s <frame-ip>:5555 shell setprop persist.adb.tcp.port 5555
adb -s <frame-ip>:5555 shell reboot
```

- This creates `/data/property/persist.adb.tcp.port` (`5555`).
- `reboot` over ADB worked: root ADB was back on 5555 **46 s later**, at a new DHCP address.
- Undo: `rm /data/property/persist.adb.tcp.port`, then reboot.

**Security:** this is root ADB with **no key check** (`ro.adb.secure=0`), open to the whole LAN
and surviving reboots. Never forward 5555. Keep the router DNS record until AiMOR is disabled: it
also stops AiMOR from reaching the vendor's root-shell server.

### 5. Back up over Wi-Fi

- Wi-Fi ADB read at about **480–560 KB/s**.
- We backed up everything before UDISK (the first 2,132 MiB of `mmcblk0`, covering every firmware
  partition), plus `mmcblk0boot0/1` and a tar of `/system/app/webview`.
- It ran in 64 MiB chunks with `/sbin/busybox dd ... | adb exec-out`. Each chunk was re-hashed on
  the frame with `busybox sha256sum` and had to match the host's hash.
- About 75 minutes in total. UDISK (`/data`) was not backed up.

All 34 chunks, both hardware boot areas and the WebView tar matched on the first read. Checks
run on the backup:
- The boot partition read from the chunks matches a separate boot read.
- `system` has the ext4 magic number.
- The MBR ends in `55aa`.
- No `0xCC` filler.

### 6. WebView 106, CA roots, kiosk, Home

All of these happened over Wi-Fi ADB. Every step followed the existing
[A33 guide](allwinner-a33-pf1007l.md), with `adb -s <frame-ip>:5555` in place of `adb -d`.

1. **WebView 106** ([guide §6](allwinner-a33-pf1007l.md#6-upgrade-webview-before-using-the-kiosk)):
   - Used the pinned LineageOS `webview.apk` (`e2edc1f8…0580`) plus its three `lib/armeabi-v7a/*.so`.
   - Staged them in `/data/local/tmp`, then copied them to `/system/homehq-new-webview` and
     verified them on the frame.
   - Moved the original tree to `/system/homehq-stock-webview` and the new tree to
     `/system/app/webview`, verified again, and remounted `/system` read-only.
   - `/system` had 406 MB free.
   - After a reboot, `versionName=106.0.5249.126`, with no dlopen errors.
2. **Kiosk:**
   - Built with `dashboard/kiosk/build.sh` (JDK 17, build-tools 34). Installed it and Rootless
     Launcher 3.9.1 as a fallback.
   - The hosted demo rendered at once: `*.workers.dev` chains to GlobalSign Root CA, which the
     stock store has.
   - The sample photos failed with `net_error -202`, because `fastly.picsum.photos` chains to
     ISRG Root X1.
3. **CA roots:**
   - Added GTS Root R1 (`f013ecaf.0`), GTS Root R4 (`5acf816d.0`) and ISRG Root X1 (`6187b673.0`)
     to `/system/etc/security/cacerts/`, 0644 root.
   - DER SHA-256 matched [the Uhale guide](si006-uhale.md). No filename collisions.
   - The photos loaded, with no more -202 errors.
4. **Home**, with no hands on the panel:
   - `am start -n com.wesbos.homehq/.MainActivity --ez home true`, then
     `am start -a android.intent.action.MAIN -c android.intent.category.HOME`.
   - Took `screencap`, then `input tap` on **Home HQ** and **ALWAYS** (at 1280×800 these were
     at 511,646 and 829,765).
   - `package-restrictions.xml` then showed `com.wesbos.homehq/.Home` with `always="true"`.
5. **Floating Back/Dashboard:** there is no SystemUI, so no nav bar.
   - `pm grant com.wesbos.homehq android.permission.WRITE_SECURE_SETTINGS`.
   - `settings put secure enabled_accessibility_services com.wesbos.homehq/com.wesbos.homehq.NavigationService`.
   - `settings put secure accessibility_enabled 1`.
   - The buttons showed over Settings and survived a reboot.
6. **OTA updater:** `pm disable com.yhk.qeota` (`API_10-usaFrame-P-L_Yes-20240603`, running as
   system). Wait for `enabled="2"` in `package-restrictions.xml` before rebooting (15 s here).

**Three `reboot`s after these changes** each gave:
- `sys.boot_completed=1` and `init.svc.bootanim=stopped`;
- Home HQ resumed with the dashboard rendered, and AiMOR **not** running;
- root ADB back on 5555 at a new DHCP address. There was **no**
  [#118](https://github.com/wesbos/photo-frame-dashboard/issues/118)-style boot-animation hang.

Wi-Fi took 14–19 s after boot. Until then Home HQ shows "Connect to Wi-Fi?" and retries, and it
loaded the page by itself once Wi-Fi was up. On one boot that screen's "Open Wi-Fi settings"
button got tapped, leaving Wi-Fi Settings in front. The floating Dashboard button gets out of that.

The frame also had three saved networks, including a probable factory one, `AAA888-2.4G`
(`scan_ssid=1`), comparable to `1YHK-03` in #135. It was left in place pending the owner.
