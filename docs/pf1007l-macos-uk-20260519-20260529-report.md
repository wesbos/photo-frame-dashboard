# PF1007L on macOS: two UK units, May `20260519` and `20260529`

Two USB-C-only PF1007L frames bought in the UK (label FCC ID `2AW9M-PORTRAIT`), both rooted with [Route U](allwinner-a33-mainline-uboot.md) from an Apple-silicon Mac, October 2026. Unit 1 runs `20260519`, unit 2 `20260529`. Both now run the Home HQ kiosk with WebView 106.

- **Unit 1:** the Route U SPL hung on every load (`usb_bulk_send ERROR -7`). The cause was DRAM byte lane **1** coming out of calibration disabled, so every odd byte read `0x00`. The build's lane 0 retrain (#74) does not cover lane 1. Retraining whichever lane is off fixed it. A U-Boot patch will follow in a separate PR.
- **Unit 2:** the U-Boot DRAM came up clean. The read-only `ums` backup dropped 100 MB in with the CPU at 1008 MHz, and completed with the CPU at 408 MHz. After the boot patch, 3 of 6 boots froze when the AIC8800 Wi-Fi started; the [boot fixes](pf1007l-boot-fixes.md) with `WIFI_DEFER=1` installed, the next boot reached the kiosk (one boot so far, on a direct Mac port).

Host: macOS 27.0.1, Apple silicon, Android platform-tools 37.0.1, U-Boot v2025.10 with `pf1007l-uboot.patch` plus the 4-bit 26 MHz eMMC, read retry and START STOP changes from [the U-Boot settings table](pf1007l-start-here.md#u-boot-settings-that-fixed-ums-problems). Built with Apple's `container` 1.3.1 instead of Docker. Compared against repository main at `9dd323e` for unit 1 and `e97c50b` for this report. Unit 1 did not try the warm-up SPL, which was not in the build at the time.

## Unit 1: the SPL hang was DRAM byte lane 1

A record of one unit: the lane 1 retrain described here is a local U-Boot change, not in the repository's build yet.

Observed:

1. The Route U U-Boot never got past the SPL: `sunxi-fel` printed "Executing the SPL... done." and then `usb_bulk_send() ERROR -7`. CPU at 408 MHz, the SinA33 device tree and `CONFIG_SUNXI_NO_PMIC` all failed the same way. "done." only means the BROM accepted the request. `sunxi-fel` then reads back `eGON.FEL`, and that read is what timed out.
2. SPLs that return to FEL at fixed points (a marker written to SRAM A2 at `0x48000`, read with `sunxi-fel hexdump`) showed the SPL reached the end of `sunxi_board_init` and died at the top of `board_init_r`, the first code that runs on the DRAM stack.
3. A FEL readback after DRAM init showed **every odd byte reading `0x00`** and every even byte correct, while `ram_size` was 1 GiB.
4. A recorder in `mctl_channel_init` (`DXnGCR0` / `DXnGSR0` saved to SRAM A2) showed: both lanes start at `0x7c000e81`. On the first training after a cold power-on, one lane's `DXnGCR0` is overwritten with a value that has DXEN clear (`0x00001c70`, `0x0406050a` and `0x000000fa` were seen). In the most detailed run this happened during the ZQ / CA calibration, before DQS gate training. That lane's `DXnGSR0` stays `0x00008000`.
5. It was lane 1 in three cold boots and lane 0 in one. The driver then sends the dead lane to its CS1 retry, which "passes" because the dead lane is left out: a 16-bit bus, 1 GiB, one dead byte lane.
6. AXP PMIC programming in the SPL failed with `-EIO` (`power_failed = -5`) on every run, so the CPU stayed at 408 MHz.

Fix: after the first DQS gate training, if exactly one lane has DXEN clear, copy the healthy lane's `DXnGCR0` onto it and train again. With it, a cold boot that had lost lane 1 trained both lanes, took the normal one-rank 16-bit path, read back a 64 KiB random pattern with no errors on either lane at `0x4A000000` and `0x4FE00000`, and `0x50000000` did not alias. `ums` came up within 2 s, and every later load in this session worked. Backup: both passes at about 7.5 MB/s, no drops.

Guesses: the PMIC writes failing leaves the DRAM supply at the AXP's power-on default, which may make one lane's calibration marginal. #103 and #36 (`ERROR -7` or no `ums` after "done.") may be the same fault. Not tested: if the retrain fails, the driver's 8-bit fallback keeps lane 0, so a boot that lost lane 0 would still fail.

## Unit 2: CPU clock during the backup, and the Wi-Fi start freeze

Observed in U-Boot:

- PMIC programming worked (`power_failed = 0`), so the SPL raised the CPU to 1008 MHz. Both DRAM lanes trained normally, with no repair needed.
- The read-only backup through the dock's USB 2 hub port dropped at 100,663,296 bytes. The frame then had no USB device and was not in FEL.
- The same build with `CONFIG_SYS_CLK_FREQ=408000000`, on the same port, completed both backup passes at 8.2 MB/s. Independent checks passed: the image matched its hash, the gzip decompressed to the same hash, and no `0xCC` runs. One clean run supports the clock as the cause but does not prove it.

Observed after the boot patch (on the dock port unless noted):

| Boot                | Result                                                                  | Last kernel line                                                  |
| ------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 1                   | froze ~20 s after ADB appeared; screen showed alternating on/off pixels | not logged                                                        |
| 2                   | froze; screen went black                                                | `AICWFDBG(LOGINFO) Start app: 00130009, 4` at 27.7 s              |
| 3                   | booted                                                                  | same line at 28.8 s, then `rwnx_plat_patch_load done` 0.3 s later |
| 4                   | booted                                                                  | same line at 27.9 s, passed                                       |
| 5 (`adb reboot`)    | froze                                                                   | same line at 43.5 s                                               |
| 6 (direct Mac port) | booted                                                                  | same line at 27.8 s, passed                                       |

- Every logged freeze ended at the AIC8800 calibration firmware start. Temperature was 44-47 °C and the load average under 2.6.
- After a freeze the screen was black or showed an alternating-pixel pattern, not the last frame, and the frame did not reset.
- `adb reboot` restarted the frame both times it was used; the restart that "hung" froze at the same Wi-Fi line.
- The AiMOR splash screen on this unit has a Recovery Mode button.
- The frame's power button only blanks the screen (early suspend); it does not restart Android.
- The kernel prints `current_limit = 500000` at 0.31 s, `1600000` at early suspend and at shutdown.
- With the [boot fixes](pf1007l-boot-fixes.md) installed (`WIFI_DEFER=1`, `POWER_FIX=0`, `NTP_SERVER=time.google.com`), the next boot, on the direct Mac port, reached the kiosk, started Wi-Fi at 42 s and passed `install.sh verify`. Only one boot so far, and not yet on the dock port.

Guesses: this is the same brown-out as in the boot fixes guide: no battery, and the radio's calibration current spike during the busiest part of boot. The frozen screen points to lost power or clock rather than a kernel lockup. Some "`adb reboot` hangs" reports may be this freeze.

## Setup after root

- WebView 106.0.5249.126 swapped in as in [section 6](allwinner-a33-pf1007l.md#6-upgrade-webview-before-using-the-kiosk). Launching the kiosk before the reboot crashed it in `WebViewFactory`, because the package manager still had WebView 44 registered. The crash also cleared the kiosk's "Always" Home choice, so the chooser came back after the reboot.
- Ten root certificates added to `/system/etc/security/cacerts` (158 to 168): ISRG Root X1 and X2, GTS Root R1 to R4, Amazon Root CA 1 to 4. Each was checked against the same root in macOS's `SystemRootCertificates.keychain` by SHA-256. Each file is in Android's format: the PEM followed by `openssl x509 -text -fingerprint -sha1`, named `<subject_hash_old>.0`.
- Router: a UniFi zone-based firewall policy, Internal → External, TCP, port list 7806 and 10546-10550, blocks AiMOR's vendor connection for the whole frame network.

## macOS notes

- In `ioreg -l` output, `idProduct` is printed before `idVendor`. A `grep -A` for the product after the vendor matches the next device.
- `container build -q` (Apple `container` 1.3.1) hung with no output; `container build --progress plain` worked.
- `sunxi-fel spl <file>` also writes the main U-Boot image to DRAM if the file contains one. Before DRAM is up that hangs the frame, so use SPL-only files for early checkpoint builds.
- The first time the frame booted on a direct port, macOS asked to allow the accessory. Until it was allowed, the device showed in `ioreg` as `!registered, !matched` and `adb devices` was empty.
